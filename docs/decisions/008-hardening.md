# 008. Hardening

## Context

The app's screens hold a balance, recipients and the PIN pad, and an Android phone can run software working against its owner: malware that captures the screen, a screen-sharing scammer, an app drawing over this one to steer a tap, or an accessibility service or remote-control app reading the screen, a common route for Android banking scams in Malaysia. A rooted or hooked phone lets other code read or change this app while it runs. Records can outlive the app: Expo's build turns Android backup on unless told otherwise, and the iPhone keychain survives deleting the app. Bank Negara Malaysia's Risk Management in Technology policy asks for a mobile app designed to run in a secure, tamper-proof environment, and among the controls an independent assessor checks a bank has in place for online transactions, it lists an app that does not run on compromised devices; neither says how. And some protections can only be built on the bank's servers.

## Decision

A production build protects what is on screen, the phone it runs on and what it stores. What only the bank's servers can do is named, not faked.

- **Screen capture.** Production blocks screenshots and screen recording on every screen except the two receipts, the result page and a transfer's details. The shell switches the block on before the first render and lifts it only once a receipt has been the current route for 600 milliseconds, an allowance meant to outlast the transition into it, so that the screen being left is not captured as it slides away; leaving a receipt puts the block back before the next screen is drawn. A new screen is blocked unless it is named a receipt, and no screen opts in. On Android a blocked screen is also blank in the recent-apps view. Receipts stay capturable because people keep a screenshot of a receipt as proof of payment. Development and demo builds allow capture, and a Demo scenario shows the block.
- **The iOS app switcher.** A blur at the library's default strength, 0.5, covers the app in the switcher, in every build, never paused. At that strength figures may stay legible. The Face ID prompt is expected to make the app inactive, so the prompt likely shows over a blurred screen; no device has confirmed it.
- **Rooted, jailbroken or hooked phones.** Production refuses approval when the signing library reports root, a jailbreak or runtime hooks: those signals, never its overall verdict, which on Android also counts a phone with no screen lock, or any error, as compromised. An unclear result, or none within 5 seconds, allows approval and logs it, since a check that never answers must not lock a genuine customer out. Every approval waits for a fresh check, since hooks can attach after launch, and leaving review while it runs cancels the press: no transfer is created and no prompt appears. The refusal takes the place of the approval prompt and offers no way to approve anyway. Development and demo builds skip the check, and a Demo scenario shows the refusal.
- **The PIN pad.** The app's own keypad, never the system keyboard. On Android, while the PIN sheet is open, the app ignores touches that arrive while another app draws over the screen. The filter covers the whole screen, because React Native hands every touch to its root view first, and the sheet says to close the app drawing over it. This is read from the code, not seen working: the emulator has no overlay app.
- **Permissions.** Writing contacts, drawing over other apps, shared storage and photo access are refused, since the app uses none of them (`app.config.ts`). The permission to detect screenshots stays, in every variant, though nothing uses it: expo-screen-capture registers for screenshot events at every launch on Android 14 and newer, used or not, and Android closes the app without it.
- **Storage.** The signing keys never leave the phone's secure hardware. The few records the module keeps, the ids of its keys and of transfers still being checked, sit in the platform's secure storage, which on iOS opens them only on this device while it is unlocked (`src/shared/platform/secure-storage.ts`). Android backup is off (`app.config.ts`), and an install marker in general storage, missing at launch after a reinstall, wipes the records and keys an earlier install left behind.
- **Logs.** An allow-list decides what reaches a log or an analytics sink. Credentials and personal data count as sensitive and never do; amounts may (`src/shared/observability/observability.ts`).
- **Rules the lint enforces.** Storage goes only through the platform module, except in the fake bank, which keeps its own state; console output goes only through the observability module; and outside `src/mocks/`, only the test harness imports the fake bank, which the shell loads through its gated `require` (`eslint.bans.mjs`). A secret scan runs with every lint.
- **The bank's side.** Proving a phone's integrity takes the bank's servers: Google Play Integrity on Android, Apple App Attest on iOS. This module names that step and builds none of it.
- **Not built: hiding the screen from accessibility services.** Android 14 lets an app mark its views so only genuine accessibility tools can read them. That needs native code, so a malicious accessibility service or a remote-control app can still read the screen. In production, that flag and the bank's server-side signals are the answer.

## Rejected

- **Blocking capture on the transfer steps only, or on those and Home.** Either leaves History, with its names and amounts, capturable, since it runs in a route stack of its own; the first leaves Home's balance and recent recipients capturable too.
- **Blocking every screen, receipts included.** People keep a screenshot of a receipt as proof of payment.
- **Never blocking.** A balance, a recipient or the PIN pad on screen could be captured by malware or a screen-sharing scammer.
- **An on/off switch for the block in the Demo menu.** It would stay on across scenarios, so the block could be shown during a bank scenario such as not enough balance, at the cost of a second kind of entry in the menu and one more field in the store behind it.
- **A switch with no matrix section.** It would be a demo-only control with no matrix id, unlike every scenario the Demo menu picks, and the matrix would never tell other clients that capture is blocked.
- **react-native-capture-protection.** Chosen instead: expo-screen-capture, Expo's own module, which both blocks capture and draws the switcher blur, at a patch that fixes an iPhone bug where blocking again on the next screen blacked out the app.
- **A full-strength blur, paused for Face ID.** The pause would switch the cover off around every approval, and anyone leaving the app mid-prompt would leave the review screen, recipient and amount, unblurred in the switcher.
- **No cover in the switcher.** A balance or a recipient's name would show to anyone glancing at the switcher.
- **expo-device's or jail-monkey's root check.** Either adds a library for a check the signing library already makes.
- **Locking review's exits while the phone check runs.** No press could outlive the person leaving review, but while the check ran, Back and the swipe would do nothing, and someone who wanted out would find the screen stuck. Chosen instead: leaving cancels the press, and they press again if they come back.
- **No on-phone root check, only a note in the write-up.** No genuine customer would ever be refused on a phone that misreports; the check refuses only on a clear signal instead, and the write-up names what it cannot do.
- **Hiding other apps' overlays while the PIN sheet is open.** It would remove an overlay rather than ignore touches through it; the guard filters the touches instead, and the sheet says why.
- **Leaving overlays as a written gap.** No native code, at the cost of a PIN pad an overlay app could steer; a small native guard closes it instead.
- **Dropping blocked touches silently.** With a harmless overlay such as a screen dimmer, the keypad would simply look dead.
- **Hiding the screen from accessibility services now, on Android 14 and newer.** It would stop a malicious accessibility service reading the marked views, at the cost of native code; the gap is named instead, for production.
- **Keeping the template's permissions.** The app would request drawing over other apps, the permission tapjacking malware relies on, and shared storage, none of which it uses, and a store listing shows every permission an app requests.
- **Keeping the screen-capture library's two permissions.** Photo access would be requested for nothing, since the library checks for it before using it; only the screenshot-detection permission came back, once refusing it crashed every launch on Android 14 and newer.
- **Patching the screen-capture library.** It would have kept the screenshot permission refused, at the cost of a patched dependency in the repository, re-checked at every SDK upgrade; allowing that one permission, granted at install with no prompt, was chosen instead.
- **Dropping the screen-capture library.** The block and the switcher blur both come from it; allowing the one permission kept them.
- **react-native-keychain.** A native module outside the SDK's versioning, where expo-secure-store is versioned with the SDK; its last release was in March 2025.
- **Encrypted MMKV.** Its encryption key would itself need the platform's secure storage: a second store for records that fit in the first.
- **A biometric lock on the stored records.** It would ask for a fingerprint at every launch-time check, and a biometric change would wipe the records.
- **Treating financial data as sensitive too.** Balances and amounts could never reach a log or an analytics sink either; amounts may, under this decision.
- **Treating only credentials as sensitive.** Recipients' IDs and registered names could reach a log; they count as sensitive here.
- **Lint bans alone, with no secret scan.** One check fewer, but a committed key or token would be left to review to catch.
- **No security checks beyond style.** A rule nobody checks is a rule someone breaks.
- **An app lock, or a mock sign-in.** Sign-in, device pairing, PIN setup and reset, and the biometrics setting belong to the host app this module runs inside; building them here adds a capability nobody asked for.
