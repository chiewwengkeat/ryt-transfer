# 011. Low mental load

## Context

The author set two principles for how this module's code is laid out, quoted as written:

> 1. Low mental load, when FE engineers view it
>    1. Low mental load means that line counts can't be too high for non-component files
>    2. Auxiliary helpers inside a file cannot be at the top, only the main exports, because viewers of the file is primarily interested in the main exports first only. Auxiliary helpers are only relevant if they're interested in fully understanding internals, which is usually not the goal (Usually the goal of viewing a file is to get a rough overview of it), so auxiliaries should generally be at the end of the file
>    3. Colocation is absolutely critical
>    4. When engineers see something, let's say some code, the less irrelevant information they see, the better. Examples:
>       1. Flat folder structure whereby attempting to view one file will necessarily have the engineer see dozens of different files unrelated to what they care about. See <code>src/test</code> folder, and <code>src/test/harness</code> folder
> 2. Unambiguity, such that different FE engineers do not easily have conflicting interpretations of the pattern for specific instances

Colocation sets a floor under file size, also in the author's words:

> The critical principle of colocation, means that the files realistically should have a floor. Meaning that for your re-architecture, splitting files for the sake of splitting it may not be a good idea, if the original file to split is not that large to begin with. … Not that large in the first place refers to about 200 lines for component files, and for tests, about 400 lines. … If it's below the floor, consolidation is preferred, though not required.
>
> The reason for consolidation is simply colocation, and reducing the number of jumps needed to understand a piece of something: Mental load.
>
> "Encapsulation" or "single responsibility" is somewhat secondary to this.
>
> Many small files means that for an engineer to understand a piece of something, he would have to jump many different places

And two asks about the file count: "I want the number of non-tooling files to be significantly reduced", and "ESLint files should not increase too much, and non-eslint tooling files should also be reduced".

Measured against them, the code fell short in many places. Test files ran to 2,710 lines, one of them 82 tests in a row with no `describe`. Helpers sat above the main code in 72 of 109 test files and 31 of 71 plain modules. `src/test` held 43 files in one flat folder, harness and repository checks together. Scenario ids were spelled four ways and a component's words were filed three ways. Modules that are neither components nor hooks had no home of their own. The repository's root listed 25 entries.

## Decision

Every rule below serves the two principles. Where two engineers could read a rule two ways, it names the case.

- **Sizes, measured on the file as committed.** A test file holds at most 500 lines, tooling tests included; a split is allowed from about 350 and encouraged from about 420, and a split's parts aim at 480 or fewer, leaving room for later lines. A test file under about 200 lines merges into another file of its unit where one can take it. A module that is neither a component nor a test stays within about 320 lines. The limits are exact numbers once applied: module floor 100, a component taking a fold 200, a module taking a fold 250, a merged harness file 250, module cap 320, test floor 200, test cap 500. They apply when a file is created, moved, split or folded; a file that later grows past one may be split then, and never must be.
- **Folds.** A module under 100 lines whose only user in app code is one file folds into that file, smallest first and repeated until nothing more folds, as long as the user stays within 250 lines, or 200 when it is a component. A module with a test of its own folds too, and its test moves to the user's tests, unless that test checks what only a direct call can see. A component whose only user is another component folds into that component's file as a private component while the file stays within 200 lines; past that, it nests in the user's `components/`. A component never folds into a module. A folded piece keeps its name and body, relocated rather than rewritten: below the parent's styles, a folded component keeps its Type-led name, takes `<Child>Props` and `<child>Styles`, a JSDoc of at most four lines and no export of its own. Some modules never fold: the one file through which app code loads the mock bank, a module loaded for its side effect, the wrappers around native libraries, a hook that calls the data library into a component, a module a route imports or that sets up the whole app while it loads, the flow store and its refresh after an approval, domain and shared components, the harness, which merges by role instead, and a module another test mocks by its path. An endpoint's `.type.ts` stays a file; a type file beside any other module folds into it while the module stays within 250 lines.
- **Main exports first.** Every file that is not a component opens with what it is for: a module with its exports, a test file with its setup and then its tests, a script with what it runs. Private helpers, constants and types follow. This app's Babel compiles `const`, `let` and `enum` to `var`, so a value read before its definition is a silent `undefined`, never an error: a value the file reads while it loads stays above its reader, under a disable line naming that reader, and `no-use-before-define` catches what is missed. The rule has no autofix, since moving a value read at load breaks the file.
- **Folders.** Every plain module and hook sits in a folder of its own, `<x>/<x>.ts`, with its test and its role files beside it. Routes, a screen's entry file, string bundles, each domain's `api/<area>.keys.ts`, test code and the scenario matrix are exempt. A hook, named `use-*`, lives in `hooks/`; any other module that is not a component lives in `lib/`. A module exporting a hook beside plain functions is placed by its main export. Both climb the same ladder as components, and a piece used by one other piece nests inside it. Tooling stays flat, each test beside its subject.
- **Imports.** `./` inside a folder, `@/` once an import leaves it, so every importer outside a folder spells a module's path the same way. Lint fails any `../` in `src/`; the one file that must climb out, the matrix scanner reading `.config/test-files.js`, says why on its line.
- **Tests.** A screen's tests sit in its `tests/` folder, the root view's too; every other test sits beside its module. Route tests split by behaviour: each behaviour's tests live in one file, named `<Screen>.<behaviour>.test.tsx`, and a screen's small behaviours share its unsuffixed file. A split or merge never adds or removes a `describe`, since that would change every full test name inside it. A helper that one screen's test files share sits in its `tests/` folder as `<Screen>.<role>.ts`. A repository check sits beside what it checks and is named `.check.test.ts`, which lets it read the mock bank and the root directly and earns it no scenario credit. The harness is sorted by role, into `setup/`, `render/`, `mock-bank/`, `doubles/`, `fixtures/` and `scenarios/`, and each role's small helpers are merged.
- **The app's root.** `src/root/` holds what exists once for the whole app and that every screen sits inside: the root view, and the modules a route imports or that set up the whole app while it loads. A piece only the root uses lives in the one domain its files import; importing none or several, it nests in the root view that uses it. A view that knows nothing about banking goes to `src/shared/ui/`. A banking-free piece stays beside its users until a second slice uses it.
- **The transfer flow's store** lives in `src/screens/transfer/flow-store/`, in four files: the store with every selector and the step analytics, the step reducers, the types and the test.
- **Strings.** A component's words sit under its own name, a folded one's included; words read by one module sit under that module's name; a screen's group holds only the words the screen file shows itself; `common` holds only words two modules share, and scenario words. Every scenario's words live in the transfer domain's bundle and its Demo menu title in the Demo menu's bundle. The shared namespace is `shared`, and no namespace is the default: every shared word is written `t("shared:…")`, and a component names the namespaces it reads, so its keys are type-checked.
- **Scenario ids.** One enum, `TransferScenarioId`, holds all 58 ids in the transfer domain. App code passes its members; tests pass the literal id, which the matrix check reads. The mock registry must hold every member, so the compiler, the registry and the matrix check together keep the enum, the registry and the matrix equal. Adding a scenario takes five edits: the matrix, the enum, the registry, its words and title, and its route test.
- **The demo contract's** type lives in its one implementation, `src/mocks/demo-layer/demo-layer.ts`, and only the root may import that type from it.
- **The repository's root** keeps only what a tool or a reader looks for by name there. The other configuration files move into `.config/`, and `eslint-rules/` stays as a marker folder that coding-agent tooling looks for, holding only a note that the rules live in `.config/eslint/rules/`.
- **Endpoint files are unchanged.** An endpoint's file keeps its rules, its call, its cache and its hook.
- **Lint holds some rules, review the rest.** Lint holds the test cap, `no-use-before-define`, main-first order (`fe/file-layout`), the `../` ban, the placement check (a test under `src/app/` included), the slice layout, the slice boundaries and the import bans. Review holds a folder per module, `use-*` modules only in `hooks/`, where tests sit, `<Screen>.<role>.ts` helpers, role files imported only from inside their folder, every size limit but the test cap, how a folded piece is written, the namespace rule for `t`, and `.check.test` for repository checks only.

**Folding comes before the read-path ranking.** The author's canonical conventions, which this repository's lint rules came from, rank one cost first: the path a reader takes to the code they need, where a hop to a well-named file is nearly free and file count is no goal. So they keep one component per file and a folder per component, exempt tests from size bands, split tests only along a named axis, and ban `max-lines`. This repository amends that ranking on purpose, on principles 1.3 and 1.4. Below the floor, a file of its own is a jump the reader pays to understand one piece, and principle 1.4 counts each one as mental load. So a small piece with one user folds into that user, and the jump disappears. The fold stops at 200 lines for a component and 250 for a module: past that, a file no longer reads at a glance, and the read-path argument takes over again. The amendments: the 500-line test cap and the 200-line test floor; the module floor, the module cap and component folds; `lib/`; a folder per module and per hook; screens' `tests/`; main exports first in modules, tests and scripts; flat tooling with tests beside; non-API type files folded into their module; and rules held by review rather than lint.

The costs: a small piece is found inside its user rather than in a folder named for it, though it keeps its name, so a search still finds it. A piece can move twice as its users widen or narrow. Adding a scenario takes five edits. Some test files stay between 424 and 498 lines, inside the band where a split is encouraged. A module and its test take two layouts, a folder each in `src/` and flat in tooling. A tiny module whose moved copy also had its imports rewritten can fall below git's rename similarity, and `git log --follow` then needs `-M30%`. And rules held by review can drift where lint would not.

## Rejected

- **A module floor of about 60 lines, or 150, or none.** At 60, most of the small single-user modules stayed files of their own; at 150, modules large enough to read alone would have folded; with none, every small module stayed a jump. Chosen instead: 100.
- **No cap on modules, or a cap of 250 or 300.** No cap leaves principle 1.1 unanswered for modules; 250 or 300 would have split the scenario registry, then at 317 lines, for a size the author does not call too high. Chosen instead: about 320.
- **A test cap of 300 or 400 lines, or no cap with describe blocks to navigate.** A smaller cap buys more files without a clearer rule, and describe blocks leave a 2,000-line file. Chosen instead: 500, which one behaviour's tests rarely outgrow.
- **Splitting every test file from 420 lines.** Those splits were among the additions that would have left more files than before, against the asks to cut files. Chosen instead: only files over 500 split, and the bands stay guidance.
- **Splitting tests by the matrix's steps, or one file per scenario.** A behaviour spans steps and scenarios, so its tests would scatter, and one file per scenario multiplies files. Chosen instead: by behaviour, one file per behaviour.
- **Holding the test floor by a lint warning, or a blocking lint.** A merge is a judgement about which tests belong together, which lint cannot make. Chosen instead: review.
- **One component per file, or folds up to 250 lines.** One per file keeps every small child a jump; 250 makes a component file too long to read at a glance. Chosen instead: folds up to 200.
- **Keeping every type file, or folding the endpoints' type files too.** The endpoints' types are the proposed API contract, read on their own; the other type files are small parts of their one module. Chosen instead: the endpoints keep theirs, the rest fold.
- **Keeping modules with a test of their own as files.** Their tests can reach the code through the user it folds into. Chosen instead: they fold, except one whose test checks what only a direct call can see, such as the history list's row helper and the demo reset's cleanup, which stay files.
- **One file per harness helper.** Eighteen of the harness's 31 files were under 30 lines, each a jump. Chosen instead: each role's helpers merged, up to 250 lines.
- **Main-first order for tests only, or as a written rule only.** Helpers sat above the main code in modules too, and a written rule drifts back. Chosen instead: lint, for every file that is not a component.
- **Main first with no exceptions, helpers in a sibling file, or define before use.** No exceptions breaks the files that read a value while they load; a sibling file is another jump; define before use puts helpers on top. Chosen instead: main first, with each value read at load marked.
- **Limiting the order rule to source and tests, or giving it an autofix.** Tooling and config files have the same readers; an autofix would move values read at load and break the file silently. Chosen instead: every file, no autofix.
- **A folder per concern, a role suffix inside `hooks/`, or a module beside its single user.** None gives a module that is neither component nor hook one home every engineer would pick, and a suffix keeps modules that are not hooks in `hooks/`. Chosen instead: `lib/` on the same ladder as components.
- **Splitting a module that exports a hook beside plain functions.** Both such modules sat below the size the floor protects. Chosen instead: each is placed by its main export, whole.
- **A folder only for plain modules, or only once a module has a test, or flat modules.** Each leaves two shapes for one kind of file, which engineers then choose between. Chosen instead: a folder for every module and hook.
- **`tests/` in every folder, or once a folder holds two test files, or tests beside the code everywhere.** Outside screens, a module's one test beside it is part of what the folder is about; a screen's ten suites are not what someone opening the screen wants. Chosen instead: `tests/` for screens and the root view.
- **The repository checks in one `checks/` folder, or left in `src/test`.** Either keeps them away from what they check. Chosen instead: beside it, with the `.check.test` suffix.
- **Reaching the mock bank and the root through the harness, keeping the three checks in `src/test`, or listing them in the lint config.** The harness route adds a module only to forward imports; a file list grows with every check. Chosen instead: the suffix, which lint keys on.
- **One `harness/` folder, the old split, or no role folders.** Each leaves the harness's helpers flat among each other. Chosen instead: role folders, merged within each role.
- **Keeping the root's folder named `shell`, with a written rule, or splitting its views from its wiring.** Either keeps views that belong to one domain, or know nothing of banking, in a folder of their own beside the app's root. Chosen instead: `src/root/`, with its single-domain views moved into their domains and its banking-free views into `src/shared/ui/`.
- **Moving every root piece to a domain with the root passing data down, or folding the account domain into transfer.** The first adds props threaded through for no reader's benefit; the second merges two business areas to place one view. Chosen instead: a piece reading one domain moves there, and one reading several stays in the root view.
- **Naming a test helper for what it does.** Chosen instead: `<Screen>.<role>.ts`, which says whose helper it is and what kind of file it is.
- **Naming the enum `TransferScenario`.** Chosen instead: `TransferScenarioId`, the name the mock bank's id type and `scenarioTest` already used.
- **The scenario ids in the flow store, or two enums with no bare strings.** Domain components could not import the flow store's list, and two enums keep two spellings. Chosen instead: one enum in the transfer domain.
- **Keeping the balance card's four scenario ids in the account domain, or an id list of the account's own.** Either keeps a second spelling of the ids. Chosen instead: the card reports what it showed, and its screens name the scenario.
- **The `@/` alias always, or relative paths inside a slice.** Always aliasing lengthens every import within a folder; relative paths across a slice spell one module's path differently from each importer. Chosen instead: `./` inside a folder, `@/` outside it.
- **A root alias for tooling.** The tooling has no `@/` alias, and one exception line costs less. Chosen instead: the ban covers `src/` only.
- **Flattening components inside each screen, or nesting at most two levels.** Either loses the rule that a piece sits inside its only user. Chosen instead: nesting inside the only user.
- **The transfer flow's bundle for scenario words, or checks reading every bundle.** The words would sit apart from the ids, or the checks would have to know every bundle. Chosen instead: the transfer domain's bundle, beside the ids.
- **Scanning the Demo menu's titles for retry words too.** The titles never show in production. Chosen instead: the scan reads the transfer bundle only.
- **A component's words under its screen's name, or all three shapes left as they were.** A component shown on two screens has no single screen to file under, and three shapes leave each engineer to pick one. Chosen instead: under its own name.
- **Renaming the namespace only, a string bundle for the root, or no change.** A bundle for the session-ended view's three strings is three files for three strings. Chosen instead: `common` becomes `shared`, and those strings stay in it.
- **`shared` as the default namespace.** Shared code could not write the `shared:` prefix, so a shared word would be spelled two ways. Chosen instead: no default namespace.
- **A lint rule against a `t` from `useTranslation()` with no namespace.** Chosen instead: review holds it, among the less important rules lint leaves to prose.
- **The demo contract in `src/root/`, or left in the approval domain.** One of its seven members concerns approval; a home in the root splits the type from the one file that implements it. Chosen instead: the type in its implementation, imported by type only.
- **The flow store in `lib/transfer-flow/`, in `transfer-flow/`, or left in `state/`; one file per step, or all in the store file.** `lib/` would have pushed it into a domain, where screens' state cannot live, and `state/` names nothing. One file per step makes small files with one user; one file passes the module cap. Chosen instead: `flow-store/`, in four files.
- **Endpoint files holding only the bank call and its cache, with the rules about what the data means moved out.** Each endpoint's rules would leave the one file an engineer opens for that endpoint. Chosen instead: endpoint files unchanged.
- **Keeping the lint rules in `eslint-rules/` at the root, or moving them with no folder left behind.** The first leaves a tooling folder among the root's entries; the second switches off the guards coding-agent tooling keys on that folder. Chosen instead: the rules move into `.config/eslint/rules/`, and a marker keeps the folder.
- **A folder per lint rule.** A rule and its test are the whole unit, so a folder adds a jump that hides nothing. Chosen instead: flat, each test beside its rule.
- **Folder per module and screens' `tests/` held by lint.** Chosen instead: prose, which review holds, so lint stays small.
- **Exempting tooling tests from the size rules.** Tooling tests ran to 976 lines, with the same readers as any test. Chosen instead: every test file.
