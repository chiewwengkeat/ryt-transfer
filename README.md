# Ryt Transfer

A money-transfer module for a Malaysian mobile banking app. You choose who to pay, enter an amount, review it, approve it with your face, a fingerprint or your bank PIN, see what happened to the money, and find it again in your transfer history. It runs on Android and iOS, built with React Native, Expo SDK 57 and TypeScript, against a simulated bank, since no real one is reachable.

Every situation a transfer can meet is described once, in plain words, in the [scenario matrix](src/screens/transfer/scenarios/transfer.md), which the tests, the simulated bank and the app's words all follow. Why the module is built the way it is: the [write-up](docs/write-up.md) and the [decision records](docs/decisions/). How to work on it: [CONTRIBUTING.md](CONTRIBUTING.md).

## Run it

### Install the demo on Android

Download `ryt-transfer-demo.apk` from the [latest release](https://github.com/chiewwengkeat/ryt-transfer/releases/latest) and install it on an Android phone or emulator: open the file on the phone, or run `adb install ryt-transfer-demo.apk` while the emulator runs. It carries code for ARM phones and emulators on Apple silicon (`arm64-v8a`) and for emulators on Intel machines (`x86_64`). It is the demo build, with the simulated bank and the Demo menu.

### Build from source

You need Node 22.13 or later on the 22 line (see `.nvmrc`), pnpm 12, and Xcode with an iOS simulator or Android Studio with an emulator. Install pnpm 12 from <https://pnpm.io/installation>, or prefix each `pnpm` command below with `npx pnpm@12.9.1`.

```sh
pnpm install
pnpm ios        # or: pnpm android
```

Expo Go cannot run this app: it carries native modules, biometric key signing and the PIN pad's touch guard among them, that Expo Go does not ship.

### Variants

`EXPO_PUBLIC_APP_VARIANT` picks the build: `development`, `demo` or `production`. Unset or empty means `production`, which has no simulated bank and no Demo menu, so a bare `npx expo start` serves an app with no backend; start Metro with `pnpm start`. Development and demo carry their own name, app id and URL scheme, so they install beside production.

| Variant                                       | iOS                   | Android                   | Android APK, no device needed   |
| --------------------------------------------- | --------------------- | ------------------------- | ------------------------------- |
| `development` (debug, served by `pnpm start`) | `pnpm ios`            | `pnpm android`            | —                               |
| `demo` (release)                              | `pnpm ios:demo`       | `pnpm android:demo`       | `pnpm build:android:demo`       |
| `production` (release)                        | `pnpm ios:production` | `pnpm android:production` | `pnpm build:android:production` |

Each script regenerates the native project for its variant before it builds: the variant is baked into the native app and inlined into the JavaScript bundle, and a fresh project leaves Gradle no stale bundle to reuse. A bare `npx expo run:*` reuses whatever native project the last variant left behind.

The last column builds a release APK into `dist/` without installing it, so no device or emulator needs to be attached.

### Checks

```sh
pnpm typecheck
pnpm lint    # ESLint, Prettier, the placement-ladder check and the secret scan
pnpm test
```

## Try every scenario

### The Demo menu

Development and demo builds show a strip across the top of every screen. Its **Demo ▾** button opens the Demo menu, which picks one scenario at a time and then closes. The strip then reads "Demo · " and the scenario's name, and its ✕ goes back to normal. A pick stays until another replaces it, through a restart too. Picks never combine.

The menu, top to bottom:

- **Unlock PIN**, marked "Demo only", is there only while the demo PIN is locked. It stands in for the PIN reset the host app would run.
- **Normal, no scenario**: the bank behaves normally and keeps what it holds, such as the balance and today's limit used.
- **No biometrics**: approval goes to the PIN, as when face and fingerprint approval is turned off in the app's settings.
- **Screenshots blocked**: production's capture block, in this build. Screenshots and screen recordings come out blank on every screen but the two receipts, the result page and a transfer's details.
- **Rooted, jailbroken or tampered phone**: production's refusal, in this build. Review refuses to approve, in place of the approval prompt.
- One heading per step, listing every scenario the bank or the connection causes, by its name in the matrix. Pick one, then walk to the step it names:

  | Step      | Entries                                                                                                                                                                                                                                                                                            |
  | --------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
  | Start     | New customer's lower daily limit · Balance or limit can't load · Transfers under maintenance · Offline · Something unexpected while starting                                                                                                                                                       |
  | Recipient | Something unexpected while choosing the recipient                                                                                                                                                                                                                                                  |
  | Amount    | Something unexpected while entering the amount                                                                                                                                                                                                                                                     |
  | Review    | Recipient not found · Name check unavailable · Too many name checks · Balance or limit short at confirmation · Phone paired less than 12 hours ago · Account opened less than an hour ago · Account locked · Name check expired · No answer when confirming · Something unexpected while reviewing |
  | Approval  | Approval key unknown to the bank · Approval window passed · Approval could not be verified · Balance or limit short at approval · Stopped by the bank's fraud check · Held for a security check · Receiving account inactive                                                                       |
  | Outcome   | Transfer processing · Refunded after processing · Something unexpected after sending                                                                                                                                                                                                               |
  | Recovery  | No answer to the approval · Bank still unreachable · Last transfer not found · Session ended · Unknown answer to the approval · Something unexpected while checking                                                                                                                                |

- **Reset demo** starts the bank afresh: the opening balance of RM12,845.50, today's limit unused, a newly seeded history, the PIN unlocked and no scenario picked.

### What the demo build does differently

Production blocks screenshots and screen recording on every screen but the two receipts, and refuses approval on a phone that reports it is rooted, jailbroken or hooked. The demo and development builds do neither by default: capture stays allowed so the demo can be recorded, and the phone check is skipped because an emulator reads as rooted. **Screenshots blocked** and **Rooted, jailbroken or tampered phone** in the Demo menu each switch production's behaviour on, in the demo build.

### Scenarios you cause yourself

The rest come from what you type or do, with **Normal, no scenario** picked unless a line says otherwise.

| Scenario                                          | How                                                                                                                                                                              |
| ------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Balance and today's limit shown                   | Open the app.                                                                                                                                                                    |
| Earlier transfer still being checked              | Pick **Transfer processing** and send a transfer. While it is still processing, start another one (review warns), or close and reopen the app (Home warns).                      |
| Badly formed ID, amount or note                   | Type a mobile number with too few digits, an amount with three decimals, or a note with symbols.                                                                                 |
| Contacts access refused                           | Tap the contacts button on the recipient step and refuse access.                                                                                                                 |
| Picked contact has no Malaysian mobile number     | Pick a contact with no Malaysian mobile number, after adding one to the phone's contacts.                                                                                        |
| Recent recipient chosen                           | After one transfer, pick its recipient from the recent recipients, on Home or the recipient step.                                                                                |
| Amount over the balance or a limit                | Type more than the balance, more than today's remaining limit (RM5,000 a day to start with), or more than RM50,000.                                                              |
| Recipient found, First transfer to this recipient | Enter any well-formed ID: the simulated bank gives each one a registered name and bank of its own, and an ID you have not sent to before gets the first-transfer warning.        |
| Details changed after no answer                   | Pick **No answer when confirming**, tap Transfer, go back, change the amount or note, and return to review.                                                                      |
| Double tap on Transfer                            | Tap Transfer twice, quickly.                                                                                                                                                     |
| Face or fingerprint recognised, not recognised    | Approve with a matching or a non-matching face or finger (below).                                                                                                                |
| Too many face or fingerprint attempts             | Fail until the phone locks recognition. The iOS simulator never locks it, and newer Android handles a lockout inside its own prompt, so the route tests cover this one.          |
| Approval cancelled                                | Cancel the prompt, or close the PIN sheet.                                                                                                                                       |
| Face or fingerprint unavailable                   | Pick **No biometrics**, or remove every fingerprint from the emulator, or turn Face ID enrolment off on the simulator.                                                           |
| Fingerprints or face changed                      | On Android, add a fingerprint in the emulator's settings once the app has set approval up. The iOS simulator never ends a key when enrolment changes, so it does not show there. |
| PIN chosen instead                                | Tap **Use PIN instead** under Transfer.                                                                                                                                          |
| Incorrect PIN, PIN locked                         | Enter any PIN but the demo PIN. The third wrong one locks it; **Unlock PIN** in the Demo menu unlocks it.                                                                        |
| Something unexpected while approving              | The route tests cover it; nothing in the demo causes it.                                                                                                                         |
| Transfer completed                                | Approve a transfer.                                                                                                                                                              |
| App closed during approval                        | Pick **No answer to the approval**, approve, close the app from the app switcher while the result is still checking, and open it again.                                          |

### Face ID, fingerprints and the demo PIN

- **iOS simulator:** turn on Features → Face ID → Enrolled. While the prompt shows, Features → Face ID → Matching Face approves, and Non-matching Face is not recognised.
- **Android emulator:** set a screen lock and add a fingerprint in the emulator's settings, touching the sensor from the emulator's extended controls (⋯ → Fingerprint) when it asks. While the prompt shows, touch the sensor with that finger to approve, or with another to be not recognised. From a terminal, `adb -e emu finger touch 1` touches with finger 1.
- **The demo PIN is `246810`.** The bank allows three tries.

## Languages

The app speaks English, Malay and Chinese, and follows the phone's language until you pick one on Home. The Malay and Chinese are machine translations, used as they came out and reviewed by no one. A glossary in the scenario matrix fixes how each language says what happened to the money, and which words for sending again no button may carry, but the translations' overall quality is unknown.

## Assumptions

- **A Malaysian bank's customer.** Ringgit only, held as whole sen, and times shown in Malaysia time.
- **Transfers go over DuitNow**, to a mobile number, an NRIC, a passport, a business registration number or an account number at a named bank. The bank, never the app, looks up the name the ID is registered to.
- **The module runs inside the bank's own app**, which already signs the customer in, pairs the phone, sets up and resets the PIN, holds the biometrics setting and manages the session. The module reads that setting and hears of a PIN reset through the two seams below, and hands a session the bank ended back to it.
- **The bank's API is designed here.** No backend exists, so each endpoint's request and response types, in its domain's `api/` folder, are a proposed contract, and the simulated bank answers it. Production calls an address that never resolves.
- **The bank creates a transfer before anyone approves it.** Creating checks the balance, the limits, any waiting period and the account lock; only the approval moves money. Every write carries an idempotency key the bank honours for 24 hours.
- **The bank's rules are the simulated bank's**: RM5,000 a day, or RM1,000 on a new account, at most RM50,000 in one transfer, 60 seconds to approve, three tries at a six-digit PIN, and a wait of 12 hours after a new phone is paired or an hour after the account opens. The app shows the limits the bank returns rather than assuming them.

## For the host app

The host app tells the module two things about its customer, both through `src/domains/approval/hooks/approval-settings.ts`:

- Its "Enable Biometrics" setting, as `biometricApprovalOn` in `approvalSettingsStore`. While it is off, approval goes straight to the PIN.
- That the customer's PIN reset has completed, by calling `notifyApprovalPinReset()`. Until then a phone whose PIN the bank locked keeps showing the locked words and opens no keypad.

## How this was built

I built this with Claude Code, Anthropic's coding agent, and this section is where I say who did what. No commit carries an AI co-author line: the repository's `commit-msg` hook refuses any trailer, and this section discloses it instead.

- **What I decided.** Every library, every feature and every rule here was my call. Before any code, Claude Code put the open questions to me in rounds, each with its options, what each would cost and a recommendation, and I picked one, sometimes against the recommendation, or answered in my own words. Questions that came up while building came back to me the same way. The [decision records](docs/decisions/) set out the larger choices and the options they beat.
- **What Claude Code did.** It wrote the code, the tests, the scenario matrix and these documents from those decisions. The work ran as parallel sessions on separate branches, each piece handed to its own agent with a written plan, and each commit is one slice of it.
- **How each step was checked.** Every commit typechecks, lints, passes the placement check and passes the tests on its own, and CI runs them again on every push. Review agents that wrote none of the code audited each piece against its plan and the source, and their fixes landed as commits of their own. The app ran on an Android emulator and an iOS simulator, never on a physical phone; the [write-up](docs/write-up.md) says what that leaves unproven.

## Next steps

- **Prove the device-bound security on real phones**: the hardware keys, the Secure Enclave, manufacturers' Android builds and the capture block on them, with a VoiceOver pass on a real iPhone.
- **Prove the phone to the bank's servers**, with Google Play Integrity and Apple App Attest, and key attestation, in place of the on-phone root check alone.
- **Hide the screen from accessibility services** on Android 14 and newer, which needs native code, alongside the bank's server-side fraud signals.
- **Have a person review the Malay and Chinese**, and walk both at large text sizes.
- **Agree the API with the bank's backend**, and replace the proposed contracts with its own.
